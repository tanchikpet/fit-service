# Справочник типов заявок и версии форм

## Управление

Администратор открывает «Типы заявок» из бокового меню. Можно создавать и копировать типы, редактировать название, описание, иконку и порядок, добавлять и переставлять разделы и поля. Поддерживаются текст, многострочный текст, число, дата, URL, список, множественный выбор и «Да / Нет». Обязательность, подсказки, значения по умолчанию и варианты сохраняются в конфигурации. У системного поля названия можно менять подпись.

«Сохранить черновик формы» обновляет рабочую конфигурацию. «Опубликовать версию» добавляет неизменяемый снимок с автором и датой. Предпросмотр использует те же элементы, что и форма заказчика. Выбор старой версии в истории загружает её в редактор, после чего её можно опубликовать как новую версию.

- Активный опубликованный тип доступен при создании.
- Неактивный тип скрыт в выборе. Ранее сохранённые черновики можно редактировать и подавать.
- Архивный тип скрыт в выборе. Его черновик можно просмотреть, подача и повторное сохранение заблокированы. Автор по-прежнему может удалить свой черновик.
- Удаление типа проверяет живые заявки и сохранённую историю. Удалённый ID не используется повторно.

## API и данные

| Метод | Изменение |
| --- | --- |
| `GET /api/form-types` | Сессия FIT Requests, актуальные версии активных типов в порядке каталога. |
| `GET /api/admin/form-types` | Администратор, рабочие конфигурации, состояния, ревизии и история публикаций. |
| `POST /api/admin/form-types` | Администратор и same-origin. Действия `create`, `copy`, `save`, `publish`, `restore`, `state`, `delete`. Запись существующего типа требует его `id` и `revision`. |
| `GET /api/requests` | Для доступной записи возвращает `formVersion` и `formAnswers`. Ответы и поля зависят от закреплённой схемы. |
| `POST /api/requests`, `PUT /api/requests/:id` | Принимают `requestKind`, `formVersionId` и `formAnswers`. Для устаревшей новой формы возвращается `409` с кодом `form_changed`. Ревизии заявок и ключи повторного сохранения продолжают действовать. |

`fit_form_types` хранит состояние, порядок, рабочую конфигурацию и указатель на актуальную публикацию. `fit_form_versions` хранит снимок, номер версии, автора и дату. `fit_form_retired_ids` не даёт повторно создать удалённый исходный тип при запуске. В таблицах заявок и аудита добавлен внешний ключ `form_version_id`. Новые ответы хранятся в `payload.formAnswers`. Заголовок остаётся доступен в `payload.title` для реестра, поиска и Kaiten.

Миграция выполняется транзакцией при старте сервиса с блокировкой параллельного запуска. Исходные три схемы получают версию 1. Значения `payload`, владельцы, даты, номера, статусы, ревизии и связи с Kaiten остаются в прежних колонках. Для записей без типа применяется прежнее правило `pageAction`. Отдельная подача заказчиком сохраняет заявку в FIT Requests. Описание карточки при ручной передаче строится по закреплённой версии.

## Проверки и ограничения

Локальные тесты с PostgreSQL 16 покрывают повторный прогон миграции, сохранность исторической заявки и аудита, публикацию, перенос старой конфигурации в новую версию, защиту истории при удалении, видимость черновика, блокировку архивной подачи, отправку неактивного типа и значения `0` и `false`. Браузерные проверки используют изолированные ответы API. Реальный Kaiten и production при проверке не использовались. Скриншоты показывают [редактор](form-admin.png) и [форму заказчика](form-customer.png) с тестовыми данными.

Сложные условия и маршрутизация вне этого этапа. Замена типа уже опубликованного поля требует нового ID поля. Формы ограничены 20 разделами, 80 полями и 100 вариантами на поле. При несовместимом обновлении открытой формы такие ответы остаются доступны для копирования до закрытия окна. Редактор истории показывает идентификатор администратора из сессии — числовой Telegram ID.

## План выпуска

1. После согласования взять резервную копию PostgreSQL и проверить восстановление. Прогнать миграцию на изолированной копии с тестовыми или обезличенными данными. Сравнить количество записей, содержимое payload, владельцев, историю, статусы и связи до и после. Оценить время блокировки таблиц при добавлении колонок.
2. Дать CI завершиться для точного коммита выпуска. Избежать параллельной записи старой и новой версиями сервиса во время перехода. Выпускать на согласованном окне с готовым резервным восстановлением.
3. После запуска проверить, что доступны только три исходных типа. Открыть старую заявку и собственный черновик, подать тестовый черновик с тем же номером. Проверить права администратора и заказчика, затем ручную отправку согласованной тестовой заявки в Kaiten.
4. Новые типы и схемы публиковать после приёмки. До их использования откат приложения возможен при сохранении добавленных таблиц. После появления версионных ответов в production использовать исправление вперёд или временно деактивировать затронутые типы. Старая версия приложения не умеет редактировать такие ответы.
