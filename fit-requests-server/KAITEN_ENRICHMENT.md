# Расширение источников Kaiten для WEB

## Основание

Переданные владельцем итоги диагностики 28.11.2026: 1 007 карточек, 1 006 доступных историй, 5 785 перемещений, из 63 диагностических запросов 58 успешных и пять HTTP 403. Активность наблюдается с 08.04.2024; каждый из шести запросов на 20 событий имел продолжение. По итогам отчёта подтверждены справочники, детальное описание и авторы перемещений. Свойств семь, ID 428033 заполнен у 510 карточек. Файл `kaiten-data-diagnostics.xlsx` в доступных вложениях отсутствовал, поэтому разбивка пяти отказов, название поля и варианты значения остаются непроверенными.

## Хранение

- `002-kaiten-enrichment.sql` применяется отдельно. В событийную таблицу добавляется nullable `author_id`. Исходные ID, время, позиция, состояние и непустой ранее записанный автор сохраняются. Состояние истории отмечает карточки с успешной проверкой авторов, включая случаи, когда в ответе авторы отсутствовали.
- `kaiten_dictionary_versions` хранит неповторяющиеся версии атрибутов с первым и последним наблюдением и временем замены. Коллекция обновляется транзакционно после получения всех её страниц. Исчезновение из успешной выдачи закрывает наблюдаемую версию, оно не устанавливает удаление сущности или точный момент изменения. Ошибка, неполная пагинация и повтор строк не закрывают версии. Дочерние коллекции привязаны к доске, колонке или полю. Для пользователя сохраняются ID, отображаемое имя и доступные признаки роли/активности. Контакты, логины, фотографии и токены не копируются.
- `kaiten_enrichment_sources` хранит последнее успешное состояние источника, его версию, дату наблюдения и отдельный результат последней попытки. Источники карточки: детали, роли участников, теги, дети, внешние ссылки, блокировки и комментарии. Родители, описания, свойства и чек-листы берутся из детального ответа. При необходимости читаются отдельные чек-листы. Детали, идентичные сохранённому JSON, и списки ID, уже покрытые им, не копируются. Пустой результат у источника с дельтой может означать, что дополнительных данных нет. Ошибки сохраняют ранее полученное содержание. Общий размер дополнений проверяется перед записями, ориентир 64 МиБ для двух новых таблиц с индексами; предел на источник карточки 256 КиБ. Проверки не учитывают WAL, старые версии MVCC и свободное место тома.
- Описания, тексты комментариев и причины блокировок доступны только в серверном хранилище. PR не добавляет маршрута их выдачи. Загрузчики обращаются только к JSON-методам, файлы и вложения не скачиваются. В штатных логах команд выводятся счётчики и общие статусы. Диагностика свойства 428033 печатает администратору структурированный вывод имен и вариантов; его следует использовать в закрытом терминале.

## Порядок выпуска после отдельного согласования

1. Проверить состояние PostgreSQL и свободное место. Согласовать окно для DDL и откат к предыдущему приложению. Ничего не читать через новый интеграционный контур до проверки целевого пространства и прав токена.
2. Применить отдельно `npm run enrichment -- --migrate` до выпуска кода, использующего колонку автора. Обычный старт сервера миграцию 002 не запускает. Старый сервер совместим с добавленными колонками. При откате приложения сохранить добавленную схему и уже накопленные записи.
3. Выполнить `npm run enrichment -- dictionaries`, проверить полноту страниц, результат каждого источника, формат поля 428033 и его варианты через `npm run enrichment -- property-428033`. Ответы 403/404 рассматривать отдельно. Прямой детальный запрос выполняется для наблюдаемых ID свойств, которых нет в списке. Название не подставляется вручную.
4. Пробная карточка: `npm run enrichment -- initial --card=ID`. Проверить повторным запуском, что одинаковые данные и версии не дублируются, при 403 сохранён успешный снимок и сотрудник не может получить новые тексты. Авторы одной карточки: `npm run history -- --card=ID`.
5. После пробного запуска завершать первоначальную загрузку партиями `npm run enrichment -- initial --limit=25`. Успехи отмечаются отдельно по источнику. После прерывания сохраняются завершённые источники. Затем запускать `pending` для изменившихся карточек и неуспешных источников. Наличие новой версии Kaiten определяется по `updated_at` из штатной синхронизации. На пилоте проверить, обновляется ли она при новых комментариях, изменениях блокировок и чек-листов. Иначе потребуется отдельный триггер или выборочная периодическая сверка, сейчас они не включены.
6. Авторы ранее сохранённых событий: отдельный запуск `npm run history -- --authors` после успешной выборочной проверки. Для коротких партий использовать явные `--card`. Ни одна из команд не планируется автоматически.
7. В «Аналитике» администратор может запустить «Целевую проверку активности Kaiten». Она выполняется только на чтение, хранит отчёт в памяти и показывает фильтры, реально возвращённые действия, HTTP и причины пропусков. Перечисленные имена действий — кандидаты, а не справочник Kaiten. Поддержка проверяется по фактическому ответу. Совпадения по конкретным ID досок/колонок/карточек ищутся локально: контракт документирует `actions`, `author_id` и даты, но не фильтр по ID сущности. Используются до двух страниц на пробу, не более 32 HTTP-запросов и 90 секунд. Обрабатываются обычный и ID-only ответы активности, ожидаемые с 01.12.2026. Изменения выводятся только как имена полей с разными значениями до и после. Для колонок демонстрируются имена из явно идентифицированных событий и примеры переходов; назначения остаются для ручного подтверждения.

## Объём и нагрузка

- 1 007 карточек × семь базовых источников ≈ **7 049 GET** при одной странице каждого. Дополнительные страницы и запросы чек-листов прибавляются. Для авторов потребуется до **1 007 GET** при первом проходе и меньше при возобновлении. Для справочников нижняя оценка — пять базовых списков, плюс два запроса на доску, один на колонку и запросы за вариантами используемых свойств. Полный итог зависит от числа досок, людей, тегов, вариантов и страниц.
- Режим дополнений выдаёт один запрос за раз, с интервалом не менее 250 мс между стартами, до трёх попыток на временные ошибки, поддерживает `Retry-After` и `X-RateLimit-Reset`. Ориентир по 7 049 GET — около 30 минут суммарно в идеальных сетевых условиях без повторов; запуск разбивается на партии. Регулярная стоимость приблизительно **7 × число изменившихся карточек** плюс просроченные попытки, страницы и чек-листы. Backfill авторов использует существующий pacing истории и её advisory lock. Не запускать партии и backfill одновременно на первом выпуске, чтобы измерить фактическую нагрузку.
- Оценка хранения без измерения ответов: при 8–30 КиБ новых JSON на карточку получатся ориентировочно 8–30 МиБ полезных данных, плюс PostgreSQL, индексы, история справочников, MVCC и WAL. До большой партии сравнить фактический прирост после 5–10 карточек и запас места тома. Версии справочников сохраняются только при изменении полезного содержимого.

## Колонки 898832 и будущая история

Колонки 3189879, 3189878, 3189992, 3189965 и 3189877 выводятся в административной таблице с наиболее частыми маршрутами и примерами ID из сохранённых событий. Группировка берёт первое наблюдение карточки в колонке; одинаковые подряд позиции склеены. Это материал для ручного решения. Имена, назначение и периоды действия без подтверждения остаются неопределёнными.

Для будущих периодов нужно начинать накапливать изменения сроков, ответственных, оценок, типов, приоритетов, свойств и связей, установку и снятие блокировок, изменения чек-листов и версии структуры WEB. До включения отдельного потока проверить, какие изменения действительно содержат пары прежнего и нового значения, и оценить глубину ленты. Текущий выпуск сохраняет версии справочников и актуальные дополнения, историю содержательных полей и поток активности массово не загружает.
