# Техническая приемка синхронизации WEB

## Исходные данные и границы проверки

На 28.11.2026 интерфейс показал 1007 карточек, 1006 доступных историй, 5785 перемещений, 4408 записанных авторов и 815 карточек с отметкой проверки авторов. По чек-листам было 23 успешных результата и 984 ошибки. Остальные семь карточных источников показали по 1006 успехов. База занимала 26 МиБ, дополнительные таблицы 4 МиБ. Это данные пользовательской приемки. Подключения только для чтения к production PostgreSQL и рабочего токена API в среде разработки нет. Повторный проход по production не выполнялся.

| Вопрос | Что установлено | Что подтверждать по production |
|---|---|---|
| 984 ошибки чек-листов | Старый загрузчик записывал ошибку без HTTP-статуса, если `checklists` отсутствовал или был `null`. Пустой массив записывался как пустой успешный результат. Та же ветка без статуса могла возникать по другим причинам, например из-за формата элементов. Документация детальной карточки описывает массив и допускает `null` у вложенных `items`. Новый загрузчик выделяет недоступное поле отдельно (запись `error` с HTTP 200), сохраняет предыдущий успех, оставляет 403/404 самостоятельными исходами. | Сверить таблицу исходов и выполнить ограниченную выборку ответов на карточках из когорты. Конкретный смысл отсутствующего ключа и `null` под рабочим токеном пока не подтвержден. |
| 815 карточек и 4408 авторов | Завершение прежнего этапа означало исчерпание критериев выбора текущего прохода, в том числе с отсечкой по времени предыдущей попытки. Наличие отметки на карточке не означает, что ответ включал каждое ранее сохраненное событие. 192 карточки и 1377 событий являются разными единицами учета. | Сопоставить карточки с отметками, ошибки и покрытие по отдельным событиям. Причина остановки ровно на 815 по имеющимся агрегатам не устанавливается. |
| Единичные ошибки источников | Новый отчет показывает пересечение HTTP 403 по семи источникам и пересечение с 403 истории. | Подтвердить по production. |
| Дубли и связи | Уникальность событий по пространству, карточке, ID события и уникальность снимка источника обеспечены текущими ключами. В отчете есть повторяющиеся ID связей, ссылки на себя и цели за пределами сохраненной выборки. | Проверить счетчики в WEB. Цель за пределами выборки может быть недоступной или находиться в другом пространстве. |

Когорта исправления чек-листов выбирает старые ошибки без HTTP-статуса и обрабатывает до 24 карточек за проход. Успешные карточки и уже классифицированные ответы HTTP 200 из этой когорты исключаются. Для авторов выбираются карточки с сохраненными событиями без автора и без индивидуальной отметки наблюдения. Каждый полученный ID сопоставляется с событиями PostgreSQL. Отдельно учитываются заполненные авторы, явное `null`, отсутствие поля, непроверенные события и неуспешное чтение. Ответ, в котором не пришел конкретный ID старого события, не меняет его наблюдение. Старый автор сохраняется.

## Наблюдения и аналитика

- Отчет показывает заполненность основных полей, покрытие и состояние отдельных источников, типы и текущие доски, а также распределение числа карточек на участника без имен. Для RR Приоритета 428033 показываются заполненность и распределение по году создания в НСК, текущей доске и типу. Отсутствующее значение остается отдельным. Текущий справочник WEB из приемки содержит 218940 High, 218941 Medium, 218942 Low. Прежняя оценка заполненности 510 карточек относится к диагностической выгрузке.
- Версии досок, колонок и дорожек используют существующие интервалы наблюдений. При синхронизации учитываются доступные конфигурационные поля в разрешенном списке. Снимки карточек отслеживают сроки, оценки, тип, приоритеты, участников, родителей и детей, блокировки, чек-листы и расположение. Изменение снимка хранится один раз с датой обнаружения. Первый снимок задает базу, `event_at` остается пустым. Изменение, отмененное между двумя чтениями, может остаться незамеченным.
- Загрузка перемещений сохраняет исходное время и идентификатор Kaiten. Ограниченная проверка активности продолжает работать с ID при отсутствии раскрытых объектов в ответе после 01.12.2026. Для восстановления изменений в 2025 и 2026 годах нужны результаты пагинации по отобранным действиям и пригодные предыдущие и новые значения. Само наличие события назначения, снятия ответственного или связи в выборке не доказывает непрерывную историю. Массового чтения активности и автоматической интерпретации действий в этом PR нет.
- Достоверно доступны состав сохраненной выборки, число созданных карточек, наблюдаемые поступления и перемещения и текущие распределения с показателями полноты. На основе загруженных данных нельзя выводить число фактически выполненных задач, KPI, соблюдение сроков и исторические распределения трудозатрат. Перенос 522 карточек остается зарегистрированными перемещениями. Колонки 3189877, 3189965, 3189878, 3189992 и 3189879 доски 898832 требуют подтверждения назначения и периода владельцем процесса.

## Скорость обновления и контроль очереди

Основные карточки продолжают обновляться штатным механизмом с существующей частотой и webhook, если он уже активен. Новый механизм включается отдельно. После успешного штатного обновления данные новых и изменённых карточек получают приоритет перед фоновой сверкой. Суточный проход начинается с них. Между суточными проходами запускается отдельный короткий проход примерно раз в 15 минут, если загрузчик свободен. Его партии обновляют до 6 карточек и до 12 историй, автор читается одновременно с историей. Партии продолжаются с минутным интервалом. При отсутствии очереди и ограничений дополнительные источники обычно попадут в следующий короткий проход. Простой приложения, предыдущий длительный проход, 429 или всплеск изменений увеличивают задержку.

Сроки, приоритеты и другие поля, уже полученные штатной выгрузкой карточек, обновляются с ней. История таких изменений фиксируется при наблюдении снимка. Ответственные, комментарии, блокировки и прочие связанные сущности, для которых Kaiten не повысил `updated` карточки, обнаруживаются фоновой сверкой. Документация подтверждает фильтр `updated_after`, но не перечисляет операции, повышающие версию карточки. Подтверждённой задержки для этих изменений пока нет. Номинальный обход при очереди в 1007 карточек и лимите 24 за сутки составляет около 42 суток. Порог допуска к сверке 14 суток. Для ускорения комментариев и других независимых изменений после приёмки стоит оценить отдельный поток событий активности или вебхуки, если рабочий токен возвращает нужные события.

Рабочая ёмкость коротких проходов при непрерывной работе без задержек — порядка 500 карточек в сутки при партии 6. Это верхняя оценка уникальных карточек, если каждая проходит за одну партию. Фактическая зависит от пагинации, конфликтов, повторов и других обращений к API. UI показывает очередь карточек и историй на момент просмотра. Если очередь стабильно растёт, сравнить количество новых кандидатов и обработанных за сутки, долю 429, длительность и метрики Railway. После устойчивого пробного режима можно повысить `KAITEN_SYNC_URGENT_CARDS` с 6 до 8, затем до 12. Защита частоты, лимит 90 HTTP-вызовов на партию обогащения и лимит до 12 историй сохраняются. Теоретический лимит звонков не равен квоте токена. Цифры повышать только после оценки фактической нагрузки. При 429 действуют `Retry-After` и ограниченные повторы. Ошибки 403/404 выделены отдельно.

## Миграция 003

| Объект | Изменение |
|---|---|
| `kaiten_location_events` | Два nullable поля без default, `author_checked_at` и `author_field_present`. Записи не переписываются при миграции. |
| `kaiten_reliability_runs` | До пяти строк на пространство с фоновым прогрессом, результатами приёмки, числом HTTP-вызовов и замерами размера БД. |
| `kaiten_observed_snapshots` | Один снимок наблюдаемых полей на карточку, первичный ключ по пространству и карточке. |
| `kaiten_observed_changes` | Отдельные строки обнаруженных изменений с предыдущим и новым снимками. Фактическая дата события `event_at` оставляется пустой при наблюдении снимков. |

DDL выполняется в одной транзакции с `lock_timeout=2s` и `statement_timeout=10s`. Добавление полей требует `ACCESS EXCLUSIVE` на существующих событиях. Это короткая блокировка при свободной таблице, без пересчёта данных и индекса по существующим строкам. Если блокировка занята, операция отменяется. Откат приложения предполагает возврат к предыдущему деплою с сохранением добавочных объектов. Миграция не вызвана при старте. Повтор проверяет схему и счётчики до и после. Независимой резервной копии production нет.

Сама DDL создаёт пустые таблицы и индексы. Основной рост появляется при накоплении наблюдений. Для планирования при 0,5–2 КиБ на карточку с накладными расходами базовый снимок 1007 карточек займёт порядка 0,5–2 МиБ. Для изменений при 20 наблюдаемых изменениях в сутки и 1–4 КиБ на запись со старым и новым значениями оценка порядка 0,6–2,4 МиБ в месяц. Это сценарий, а не замер. Карточки с длинными списками увеличивают размер, а TOAST и свободные страницы меняют физический рост. Приёмка показывает разницу `pg_database_size` с индексами, но в неё могут войти параллельные записи штатного приложения. Размер тома и WAL нужно сверять по Railway Metrics отдельно. Хранилище наблюдений ограничено 64 МиБ. Значение `KAITEN_SYNC_DATABASE_LIMIT_BYTES` устанавливается с резервом по фактическому свободному месту тома. Без этого лимита новые проходы не запускаются.

## История и изменение API с 01.12.2026

Регулярная синхронизация сохраняет различия между снимками с датой наблюдения. Массового или инкрементального сохранения ленты активности в базу нет. Ранее реализованная целевая диагностика читает ограниченную выборку событий активности и проверяет наличие ID, дат и пар старого/нового значения. Перемещения продолжают использовать фактические события отдельного API истории карточки. Согласно документации Kaiten, с 01.12.2026 00:00 UTC лента дополнительно перестаёт раскрывать связанные объекты. Диагностика читает плоские `card_id`, `board_id`, `author_id` и другие ID и использует раскрытые объекты как совместимый запасной вариант. Тест проверяет ответ с ID без раскрытых объектов. Удаление объектов само по себе не подтверждает сохранность пар старых и новых значений для всех действий.

## Приёмка с телефона

1. После отдельного согласования выпустить версию с выключенным расписанием. В «Аналитике → Синхронизация Kaiten» снять исходные контрольные агрегаты. Отчёт доступен до 003, при наличии 002. Сверить HTTP 403, покрытие, связи и приоритет.
2. В этом же блоке нажать «Проверить готовность миграции 003», сверить счётчики, подтвердить и нажать «Применить миграцию 003». Операция использует только фиксированный SQL из репозитория, существующую проверку роли администратора и Origin, одноразовое подтверждение на пять минут, блокировку фонового загрузчика и транзакцию. При ошибке загрузка недоступна. Никаких SSH, публичного доступа PostgreSQL или нового тарифа не требуется.
3. Подтвердить запас тома в Railway Metrics и установить лимит размера БД согласованным изменением конфигурации. Запустить «Контрольный проход». После завершения открыть техническую диагностику и сверить длительность, HTTP-запросы с повторами, разницу размера базы, исходы и остаток очереди. Закрытие вкладки не прерывает обработку.
4. В техническом разделе при необходимости отдельно нажать «Перепроверить ошибки чек-листов» или «Дополнить авторов перемещений». Каждый запуск проверяет только свою когорту, до 24 карточек чек-листов или 48 историй за завершённый проход. Итоги каждого сохраняются отдельно. Остаток затем может обработать ежедневный проход; ежедневная перепроверка всей базы не нужна.
5. После согласования метрик и фактической сверки включить `KAITEN_SYNC_DAILY=true`. При необходимости отключить новые автоматические проходы настройкой или вернуть прежний деплой. DDL отката не требуется.
