# Аналитика Kaiten

Раздел доступен администратору FIT Requests после входа через Telegram. Страница `/app/analytics`, JSON `/api/analytics` и Excel `/api/analytics.xlsx` читают PostgreSQL. Excel формируется с теми же фильтрами и правилами на момент скачивания.

## Источники и показатели

Действующая синхронизация `/api/latest/cards` сохраняет одну строку на карточку и обновляет её поля и JSON при более свежем или равном `updated`. Вебхук инициирует ту же сверку. Пропуск карточки в списке сам по себе не удаляет строку. Дата создания, признаки состояния и связи с родителями берутся из сохранённого JSON.

История хранится отдельно от снимков. Связка пространства, карточки и исходного ID события защищает от повторных вставок. В историю входят ID доски, колонки, подколонки, дорожки и спринта, время события и `condition`. `timestamptz` хранит абсолютное время. Группировка и отображение используют `Asia/Novosibirsk`. Результат последней попытки, её время и время последнего успеха хранятся отдельно по карточкам. HTTP 403, HTTP 404, прочая ошибка и успешный пустой ответ различаются. Записанные события сохраняются при любых последующих ответах.

- **Создано** — уникальные сохранённые карточки по `created`. Выбор доски использует текущий снимок. Архив сохраняется в выборке.
- **Первое поступление на доску** — самое раннее доступное событие с ID выбранной доски, найденное до применения периода. Карточки, ушедшие с доски, учитываются. Архивирование или возврат на ту же доску не создают повторного первого поступления. Первое наблюдение может быть переносом или фиксацией уже существующей позиции. Без выбранной доски показатель недоступен.
- **Текущий состав** — последний сохранённый статус и положение карточек. Период применяется к месячным показателям. Дата последней успешной синхронизации показана отдельно от диапазона успешных загрузок истории. Из-за инкрементального обновления строки могут иметь разные даты снимка.
- **Родитель** — текущие `parents_count` и `parents_ids` для всех показателей. Одна карточка с несколькими родителями учитывается один раз. Неизвестная иерархия видна в охвате и исключается из обоих фильтров по наличию родителя.
- **Охват** — все сохранённые карточки после фильтра родителя, независимо от текущей доски. Положительные значения и нули относятся к доступной выборке. При отсутствии основания для расчёта отображается «Нет данных». Будущие месяцы не выводятся. Месяц с актуальностью внутри месяца отмечен как неполный. Для сравнения годов выбирайте одинаковые завершённые месяцы.

## Справочник этапов

`src/kaiten-process.json` хранит версию и интервалы соответствия `spaceId`, `boardId`, `columnId` → этап. Время начала включается, граница окончания исключается. Открытый интервал действует до следующего подтверждённого изменения. Для изменения добавьте новую версию, закройте предыдущий интервал и откройте следующий. Пробелы и неоднозначные интервалы дают неподтверждённый этап. Текущие названия из API не используются для подстановки исторического смысла.

Для пяти колонок доски «Разработка» интервал начинается с даты снимка 26.11.2026, на которую в Excel зафиксированы проверенные ID и названия. Более ранние интервалы этих колонок остаются неподтверждёнными. Отчёт показывает неизвестные пары доски и колонки из событий и текущих карточек, включая сами ID. Обозначение этапа «Готово» в составе описывает позицию карточки.

## Порядок выпуска

1. На тестовом окружении примените миграцию `npm run history -- --migrate`. Она же входит в существующий `setupDb` при старте сервера. SQL можно применить отдельно из `migrations/001-kaiten-history.sql`.
2. После штатной синхронизации карточек проверьте несколько ID командой `npm run history -- --card=ID --card=ID`. Команда использует существующую серверную конфигурацию. Указанные ID должны принадлежать сохранённой выборке пространства.
3. После согласования выпуска запустите `npm run history` для первоначального заполнения и последующих обновлений. По умолчанию выбираются карточки без успеха, с ошибкой или с обновлением Kaiten после начала предыдущей попытки. Явная полная перепроверка — `npm run history -- --all`. Раздел отчёта не запускает загрузку. Повторный запуск можно поставить в согласованное расписание с учётом допустимой нагрузки.
4. Проверьте охват, интервалы справочника, несколько карточек с переходом между досками и выгрузку отчёта. По итогам команды сравните `loaded`, `empty`, `forbidden`, `not_found` и `error`. При недоступных историях или сбоях команда возвращает ненулевой статус, сохраняя уже загруженные данные.

[Контракт Kaiten](https://developers.kaiten.ru/cards/retrieve-card-location-history) описывает массив событий и не указывает пагинацию. Неожиданный формат, частичный ответ или ссылка на следующую страницу отмечаются как ошибка загрузки. Два обработчика начинают запросы с интервалом от 150 мс. Временные ошибки повторяются до трёх раз с задержкой. Для 429 учитывается [время сброса лимита Kaiten](https://developers.kaiten.ru/), также поддерживается `Retry-After`. При длительной задержке карточка остаётся для следующего запуска. Загрузка защищена от одновременных запусков через PostgreSQL advisory lock.

## Решения владельца процесса

- **Выполнение.** Нужны даты существования исторических досок и колонок, значения неизвестных ID, роль «Демо» и «Готово» в приёмке, отдельные признаки отмены, правила первого выполнения, повторной приёмки и возвратов. Архив и перенос сами по себе выполнения не подтверждают. Уточните учёт дочерних задач, задач с несколькими родителями и период до восстановления исторических соответствий.
- **Производительность.** Нужны согласованные единица учёта, этап начала работы, этап окончания, правила пауз, возвратов и повторного выполнения, сопоставимые исторические границы и единицы оценок и трудозатрат. Назначение ответственного в момент работы требует исторического источника.
- **Сроки.** Нужны история согласованного срока и его изменений, момент фиксации обязательства, событие фактического завершения, правила отмены и задач без срока, календарь и часы отсечения.
- **Охват и выпуск.** Подтвердите границы пространства и трактовку массовых переносов в отчётности, перечень пользователей отчёта и периодичность фоновой догрузки. Для утверждения полноты нужна проверка покрытия за пределами сохранённого списка. Массовый перенос 16.01.2026 сохранён в подсчёте поступлений.

## Проверки

`npm test` проверяет расчёт, границу месяца, интервалы и ошибки API. Для интеграционной проверки поднимите отдельную тестовую PostgreSQL и передайте `ANALYTICS_TEST_DATABASE_URL`; тест создаёт и удаляет изолированную схему. В CI для этого используется PostgreSQL 16. Локально также проверены сценарии формы заявок и открытие аналитики в Chromium, применение фильтров, скачивание Excel и отказ в доступе сотруднику и анонимному пользователю. Во время локального прогона выполняются только запросы к тестовой БД и подставным ответам Kaiten.

Сверка с `FIT_SERVICE_statistics_2025_2026.xlsx` рассчитана из листов карточек и событий на дату снимка 26.11.2026, 17:18 НСК, с историей до 17:29 НСК. Совпали 276 числовых значений созданий и 207 значений первых поступлений по месяцам, доскам и иерархии. В снимке 1006 карточек, 1005 доступных историй, 5777 уникальных событий, один HTTP 403. Создано 399 карточек в 2025 и 432 в доступном периоде 2026. В январе 2026 на «Разработке» впервые наблюдаются 540 карточек, из них 522 — 16 января. Ноябрь 2026 отмечен как неполный, будущий декабрь исключён.

## Управление загрузкой из браузера

Администратор может выполнять загрузку на странице `/app/analytics`. Запуск и остановка принимаются только с того же адреса, что и приложение. Контрольный статус обновляется отдельно от фильтров отчёта.

1. Нажмите «Проверить готовность». Проверяются таблицы и индексы, доступ к истории Kaiten, блокировка загрузчика и доступные ресурсы контейнера. Размер базы и свободное место контейнера показаны отдельно. Свободное место именно тома PostgreSQL проверяется в Railway Metrics.
2. Нажмите «Пробная загрузка». Загрузчик повторяет одну и ту же партию из пяти или шести карточек. Во втором проходе ожидается ноль добавленных событий. Недоступность отдельных карточек учитывается отдельно, для успеха нужны минимум пять доступных историй. Ошибка запроса после повторных попыток останавливает выдачу новых карточек.
3. Проверьте свободное место тома PostgreSQL и нагрузку в Railway Metrics, отметьте проверку и нажмите «Загрузить историю». Запускается штатный режим pending. Через 30 минут готовность требуется проверить заново.
4. «Остановить загрузку» прекращает выдачу новых карточек. До двух уже начатых операций могут завершиться. При возобновлении загрузчик читает сохранённое состояние карточек и подбирает оставшиеся.

В рабочей конфигурации один экземпляр приложения. Он хранит ход текущей операции и результаты проверки в памяти, а события и состояние каждой карточки сохраняет транзакциями в PostgreSQL. Закрытие вкладки не прерывает операцию. После перезапуска приложения повторите проверку готовности и пробную партию. Переданные в БД события сохраняются. При нескольких экземплярах для интерфейса управления потребуется общий источник состояния заданий. Блокировка PostgreSQL действует и при запусках через CLI. Суточное расписание выключено.

## Диагностика данных

В аналитике администратор раскрывает блок «Диагностика данных Kaiten», запускает проверку и обновляет страницу для просмотра результата или скачивания Excel. Задание выполняется сервером, пока работает экземпляр приложения. Отчёт хранится в памяти и исчезает после перезапуска.

Агрегация выполняется в транзакции PostgreSQL `REPEATABLE READ READ ONLY` с тайм-аутом запроса. Отчёт содержит ключи верхнего уровня JSON, отдельные колонки БД, наблюдаемые числовые ID свойств и ограниченную выборку единиц измерения. Известные аналитические ключи, отсутствующие во всей выборке, показаны отдельно от явного null. Сырой JSON карточек не передаётся в отчёт.

Сервер выполняет до 70 последовательных GET-запросов к настроенному домену Kaiten. Форма не принимает ввод URL, SQL, дат или ID. При 401 или 429 дальнейшие вызовы останавливаются. Запрос ограничен 7 секундами, этап API — 120 секундами. Частичный отчёт сохраняет выполненные проверки и причину пропуска остальных. Выводятся HTTP-статус, количество записей, метаданные полей и временные границы наблюдений. Произвольные названия колонок, значения пользовательских полей, тексты и расширенные профили исключены.

Активность проверяется по первой странице трёх 14-дневных окон в каждом году 2025 и 2026. Дополнительные запросы с одной записью локализуют нижнюю границу доступной активности при рабочих фильтрах дат. Проверка не устанавливает срок хранения данных Kaiten и не доказывает, что между окнами нет пропусков. Историческое название выводится только при обнаружении конкретного изменения в проверенной активности. Назначения и интервалы берутся из существующего подтверждённого справочника приложения.

Локальная проверка использует отдельную временную PostgreSQL и подставные ответы Kaiten. Для фактического подтверждения прав и глубины истории WEB требуется запустить диагностику в рабочем приложении после согласования и развертывания этой версии.
