# FIT Requests — Kaiten sync backend (prototype)

Серверный компонент для личного FIT Requests; **не является публичным API и не должен хранить данные в GitHub Pages**. Статика продолжает работать независимо от этого сервиса.

## Возможности

- Node.js 22 + PostgreSQL, отдельная папка `fit-requests-server/`.
- При запуске создаёт необходимые таблицы и выполняет первоначальную загрузку карточек из пространства Kaiten WEB (`space_id=332384`).
- Полная первоначальная синхронизация с постраничным получением. Далее инкрементальные обновления по `updated_after` с перекрытием в 2 минуты, каждые 15 минут.
- Событие webhook запускает внеочередную сверку через API; содержимое входящего webhook **не считается источником истины**.
- PostgreSQL advisory lock блокирует одновременные синхронизации нескольких экземпляров приложения. Неудачная синхронизация не продвигает курсор.
- Поля `size` / `size_text` / `size_unit` хранятся без попытки сложить несовместимые шкалы Ершова и Олейникова.
- Сохраняет участников `members`, `owner_id` и оригинальную Kaiten-карточку в JSONB, не делая ошибочного вывода об исполнителе по `owner_id`.

## Локальный запуск

Нужны Node.js 22+, PostgreSQL и реальные параметры в защищённом окружении.

```bash
cd fit-requests-server
npm install
npm test
npm start
```

Скопируйте список переменных из `.env.example` в локальную систему окружения (Node.js **сам не загружает** файл `.env`; можно запустить `node --env-file=.env src/server.js` только локально). Никогда не коммитьте значения.

## Railway deployment

1. Подключите Railway к GitHub и создайте проект из `tanchikpet/fit-service`, рабочая ветка — `feature/kaiten-sync-backend` до проверки и слияния.
2. Укажите **Root Directory**: `/fit-requests-server`.
3. Добавьте управляемый Railway PostgreSQL в тот же проект. Передайте сервису `DATABASE_URL` через reference на переменную базы (не копируйте URL в исходники).
4. Добавьте **закрытые** переменные `KAITEN_API_TOKEN`, `ADMIN_API_TOKEN`, `KAITEN_WEBHOOK_SECRET`, `KAITEN_BASE_URL`, `KAITEN_SPACE_ID`. Для двух секретов используйте независимые строки длиной 32+ символа. Не отправляйте токены в чат.
5. Приложение слушает `0.0.0.0:PORT` и предоставляет `GET /healthz`; настройте Healthcheck на `/healthz` (он проверяет живость процесса, а не Kaiten).
6. Не размещайте `ADMIN_API_TOKEN` в JavaScript на GitHub Pages. `GET /api/cards` и `GET /api/sync/status` доступны **только при серверном заголовке** `Authorization: Bearer <ADMIN_API_TOKEN>`.
7. Для webhook используйте адрес `https://<домен>.up.railway.app/webhooks/kaiten/<KAITEN_WEBHOOK_SECRET>` и включите события изменения карточек/участников/оценок. URL — секрет: не публикуйте его и не отправляйте в чаты; учтите, что прокси могут записывать URL в логи, поэтому желательно отключить access logs для этого пути.
8. Проверьте `GET /healthz` (ответ `{"ok":true}`), затем `GET /api/sync/status` **с заголовком Authorization** из защищённого клиента. Без заголовка должно быть 401.
9. После проверки дополнительно настройте ограничения доступа к служебным endpoints на уровне сети/прокси, регулярные бэкапы PostgreSQL и мониторинг ошибок.

**Важно:** в текущем сервере нет пользовательской авторизации и клиентского прокси. Он **не подключён** напрямую к публичному интерфейсу FIT Requests. Не вводите корпоративные данные в прототип, пока не будет защищённого доступа к ним.

## Endpointы

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| GET | `/healthz` | Публичный | Простой ответ о живости процесса |
| GET | `/api/sync/status` | ADMIN Bearer | Дата последней успешной сверки, ошибки, число карточек |
| GET | `/api/cards?limit=50&offset=0` | ADMIN Bearer | Постраничный список сохранённых карточек |
| POST | `/api/sync` | ADMIN Bearer | Принудительная синхронизация |
| POST | `/webhooks/kaiten/<WEBHOOK_SECRET>` | Секрет в URL | Принять webhook и поставить синхронизацию в очередь |

## Технические ограничения / дальнейшие проверки

- Kaiten API-клиент проверялся ранее для GET карточек и `updated_after` в пространстве WEB. **Загрузка всех страниц при помощи `offset` в живом аккаунте ещё не проверялась**; проверьте до продакшена.
- Фактический payload Kaiten external webhook ещё не проверен. Приёмник принимает любой корректный JSON-объект и использует его только как сигнал для повторной загрузки из Kaiten API; формат полезной нагрузки ещё требуется проверить. Сигнатура Kaiten не подтверждена, поэтому применён независимый секрет URL.
- Прототип не реализует удаление карточек из Kaiten, архивирование синхронизируется только при наличии изменённой карточки; периодическую полную сверку полезно добавить.
- Проекты и задачи в локальном `localStorage` пока не связаны с базой синхронизации. Для этого нужен защищённый серверный API с логином и отдельным хранилищем заявок.
- Дочерние карточки, оценки и статусные правила №128–138 потребуют отдельной серверной модели и проверки реальных структур Kaiten.
- Масштабирования на несколько процессов без контроля очереди и доступа к логам нет. Административные токены должны ротироваться и не храниться в Git.

## Безопасность

Секретные переменные живут только в защищённых настройках хостинга. Доступные пользователю пути не сообщают идентификаторы карточек без admin Bearer. Сырой payload webhook не записывается в БД. Логируйте только ошибки без чувствительных деталей; задайте политику хранения данных и резервного копирования.
